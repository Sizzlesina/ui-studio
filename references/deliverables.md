# Project Deliverables

For standard implementation tasks, **deliver the code and UI directly** to the target files; separate documentation files are not required unless explicitly requested.

When the user asks for architectural documentation or design artifacts, create the following under `docs/ui-design/`. Keep them concise, accurate, and proportional to the task scope.

---

## project-analysis.md (Only when documentation is requested)
- Project concept, audience, main user journeys, and key problems solved
- User choices: style, typography, palette, identity
- Main section map: purpose, key content, primary actions, mobile treatment
- Assumptions, dependencies, and scope boundaries

## design-spec.md (Only when documentation is requested)
- Design direction summary and visual personality
- Typography: font families, weights, scales, line-heights, and RTL support
- Color palette: semantic roles (primary, surface, border, feedback) and WCAG contrast
- Spacing scale, border radii, elevation, and component interaction states (hover, focus, disabled)
- Accessibility, touch targets, and motion principles

## technical-notes.md (Only when technical notes are requested)
- Framework/stack conventions observed
- Modified files, components, and styling setup
- State handling, interaction behavior, and validation rules
- Responsive/mobile behavior and performance notes

## Previews & Wireframes (When requested)
- If requested, store preview HTML files under `design-previews/` (e.g., `design-system.html` or `wireframe.html`).
- Make wireframes lightweight and semantic to demonstrate layout, hierarchy, and navigation.

## Final Summary in Chat (Always, concise)
Provide a brief, clear summary in the user's language:
1. What was built or modified
2. Key design and UX improvements made
3. Files changed and clickable links
4. Any relevant next steps or open items
